## On-demand playing-now identity (0.2.0)

The [official submission format](https://listenbrainz.readthedocs.io/en/latest/users/json.html) documents `playing_now` as temporary state, without `listened_at`; permanent history requires a separate `single` or `import` submission. `POST /1/submit-listens?return_msid=true` returns a recording MSID for feedback before a completed listen exists. This behavior was also checked against `submit_listen` in [the upstream API implementation](https://github.com/metabrainz/listenbrainz-server/blob/master/listenbrainz/webserver/views/api.py) on 2026-10-24.

This plugin enables that fallback only inside its explicit Love action, rechecks current playback before sending it, and rejects completed-listen types and timestamps at the transport boundary. Existing exact identities retain priority. `playing_now` may also expose an existing MSID in `track_metadata.additional_info.recording_msid`.

## Source metadata and Material integration (0.3.1)

Compared LMS 9.1.1 `AudioScrobbler::Plugin::_getMetadata`, `checkScrobble`, and `API::ListenBrainz::getMetadata/_getTrackMetadata` with this plugin's capture path. AudioScrobbler reads `track->musicbrainz_id` for remote tracks too and falls back to `track->secs` when the protocol handler omits duration. The previous adapter omitted both. The adapter now preserves these sources; fresh explicit provider MBID/duration retain priority. No new remote lookup or completed-listen submission is introduced.

AudioScrobbler's `newsongCallback` first resolves `Slim::Schema->objectForUrl({url => $url})`. A playing Song's RemoteTrack may have a different ID and metadata from that canonical object. Version 0.3.1 mirrors this lookup before capturing source metadata. Material selection resolves a different selected ID through `Slim::Schema->find('Track', $id)` and requires the same exact current URL. Tests reproduce both differences; the metadata diagnostic exposes both object IDs and their MBIDs.

The [Material customisation documentation](https://github.com/CDrummond/lms-material/wiki/07-Customisation#custom-menu-entries-and-actions) documents plugin action registration since 6.4.6, `track` and `queue-track` contexts, native icon names, and `lmsbrowse`. Source review against installed version [6.4.14](https://github.com/CDrummond/lms-material/tree/6.4.14) confirmed `Plugin::registerCustomAction`, post-load `plugin-actions`, `$ITEMID` substitution, and native browse result rendering. Registration occurs in `postinitPlugin`, after plugins have loaded, and Material remains optional. A selected item ID is checked against the current track before any Love; stopped playback is still rejected. The heart action does not alter ratings or replace service-specific shuffle/repeat buttons.

The read-only `listenbrainzlove metadata` player query exposes the object/provider/effective IDs for live comparison without ListenBrainz reads or writes. Tests cover missing provider fields, precedence, registration without network activity, selected-item guards, async result handling, and Unicode labels.

## Metadata lookup and targeted feedback (0.4.0)

The user-requested [Lookup MBIDs example](https://listenbrainz.readthedocs.io/en/latest/users/api-usage.html#lookup-mbids) uses GET `/1/metadata/lookup/` with `artist_name` and `recording_name`. Version 0.4.0 follows that flow and sends optional `release_name` when available. The [endpoint reference](https://listenbrainz.readthedocs.io/en/latest/users/api/metadata.html) now requires `Authorization: Token ...`. Its optional expansion parameter is `inc`, while the older example spells it `incs`; this plugin requests no expansion and sends neither parameter. Release metadata is a hint, not proof of recording identity.

Checked [metadata_api.py](https://github.com/metabrainz/listenbrainz-server/blob/7d9a3d6f9d5283871d1aa48c9fa5301a1f4f8241/listenbrainz/webserver/views/metadata_api.py): `MAX_MAPPING_QUERY_LENGTH=250`; the sum is measured in Unicode characters before percent encoding. Both core and transport enforce that limit without truncating titles or versions. Empty `{}` is no-match; a nonempty incomplete response is an error. Candidates must contain a valid recording UUID, nonempty recording/artist names and compatible normalized names including all version words. The basic response does not supply duration, so this lookup does not claim to verify candidate duration.

The [recordings API](https://listenbrainz.readthedocs.io/en/latest/users/api/recordings.html) documents GET `get-feedback-for-recordings` with `recording_mbids` and/or `recording_msids`. This replaces first-100 favorites readback and also supplies read-only state. The implementation queries at most one of each type; it accepts score zero as known not-loved, checks exact requested IDs, and requires a shared row when verifying a write containing both IDs. [Upstream helper](https://github.com/metabrainz/listenbrainz-server/blob/7d9a3d6f9d5283871d1aa48c9fa5301a1f4f8241/listenbrainz/webserver/views/feedback_api.py#L203-L230), [zero-score pseudo records](https://github.com/metabrainz/listenbrainz-server/blob/7d9a3d6f9d5283871d1aa48c9fa5301a1f4f8241/listenbrainz/db/feedback.py#L235-L299).

Existing IDs are collected by type. Playing-now MSID does not short-circuit the bounded recent lookup. A mapped MBID wins; an MSID accompanies it only when the same accepted listen explicitly pairs them. Multiple MSIDs paired with one MBID do not need arbitrary selection: the MBID can be submitted alone. Conflicting MBIDs or ambiguous MSID-only matches fail closed.

Positive metadata lookup cache: exact source URL + metadata + username + algorithm version, SHA-256 key, 128 entries, one-hour TTL. No negative-result or credential cache. Available ISRC is captured for diagnostics and future resolver use; no ISRC-to-MBID API is introduced in this release. A network error or rejected candidate never silently falls through to a new identity.

Material's registered context entry is a static navigation icon. It opens a native bounded status list with verified filled/outline/unknown icons and a separate explicit Love action. No skin JavaScript, ratings hook, custom.js or background playing-now is installed. The existing TrackInfo Love action remains available alongside a read-only status link. Transport rejects Unlove, completed listens and manual mapping writes.

## Distribution repository format

The Material 6.4.14 renderer changes an untyped go action without an image into a text row. Its `doTextClick` uses a plain command for plugin verbs and omits list index/count arguments, so a tagged selection can be consumed as a positional argument. Version 0.4.1 sets `type=link` explicitly on both native Love and Refresh actions. This was isolated during live read-only testing, reproduced in regression assertions, and corrected without removing the selected-track guard.

## Non-playing selections and visible state (0.5.0)

The [feedback format](https://listenbrainz.readthedocs.io/en/latest/users/feedback-json.html) accepts recording MBID and score independently of any listen. Version 0.5.0 resolves the selected numeric Track ID, captures that track's URL and metadata, and allows verified feedback while another track plays, playback is stopped or the queue is empty. It never substitutes the current track for an invalid ID. TrackInfo already supplies its selected URL/object to providers; the same capture path now serves its selected-track actions.

Only matching current playback may supply playing-song MBID or forceCurrent. Inactive remote selections need positive object duration and complete provider artist/title metadata, avoiding indefinite stream station records. Playing-now fallback is enabled only for a snapshot matching actual active playback, then rechecked immediately before submission. No-match on a non-playing selection cannot manufacture a listen or now-playing notification.

Live read-only verification also exposed Material's short-list optimization: if a list contains only one distinct image, browse-resp.js clears all images. A distinct refresh icon preserves the state heart for both loved and not-loved lists. Explicit link rows route clicks on state/results to the read-only state command. No Material source files or ratings are modified.

## Complete performer credits (0.5.1)

TIDAL's [API cache](https://github.com/michaelherger/lms-plugin-tidal/blob/main/API.pm#L154) stores a scalar primary `artist` alongside a full `artists` collection. Its [importer](https://github.com/michaelherger/lms-plugin-tidal/blob/main/Importer.pm#L312) maps MAIN and FEATURED to TRACKARTIST while keeping COMPOSER and CONDUCTOR separate. The adapter previously read only the scalar field, losing a featured artist before lookup validation. This reproduced the reported Memória failure: the input had only ROSALÍA, while the accepted upstream recording credit was ROSALÍA & Carminho.

Version 0.5.1 retains MAIN/FEATURED performer names from remote metadata, or ARTIST/TRACKARTIST via the local Track object's `artists` method. It deduplicates names with the primary artist first and joins them with ` & `. Other contributor roles are excluded. The complete captured credit participates in lookup, matching, exact-source cache keys and the playback guard. Artist/title/version matching is unchanged: a missing guest, different performer or changed version still cannot pass. No relaxed prefix/substring match or new fallback is introduced. Adapter and core regressions reproduce the original failure and verify MBID-only feedback without listen submission.

## Production Material action scope and TrackInfo popup (0.7.1, 0.7.2, 0.7.3)

The installed Material 6.4.14 bundle declares `doCustomAction(a,b,c)` and directly evaluates `doReplacements(a.script,b,c)`. The unminified source uses the argument names `action, player, item`; action scripts cannot depend on those local names surviving production compilation. The loader now captures `arguments[1].id` and `arguments[2].id` before asynchronous loading. The custom.js button loader uses explicit nulls and has no action-scope dependency. IDs remain values; no unescaped metadata substitutions enter executable JavaScript, no DOM selection is guessed and no missing selection falls back to the playing track.

The older TrackInfo Love entry only provided an OPML URL callback, separate from the direct context-menu action. It did not request a native result popup. Its Jive `go` action now targets the selected ID with `listenbrainzlove love` and `popup:1`, with `nextWindow: refresh`. This is a native LMS menu contract: XMLBrowser merges the explicit Jive action, and Material's `browseHandleNextWindow` uses a single text result as the popup and retains the parent view. Version 0.7.2 also leaves the source item type unset: the installed Material deferred bundle infers a text action from its explicit go/nextWindow contract. An explicit link uses browseDoClick and bypasses browseHandleTextClickResponse, so it navigates into a submenu despite nextWindow. The result is deliberately text without a further write action; it comes from the completed verified operation. Version 0.7.3 uses refresh rather than parent: a text action has not opened another page, so parent would return from the detail view to the home page. The initial test executed the installed popup helper but supplied an already-parsed response; this missed the parser conversion described in the 0.7.4 correction below. The OPML callback remains available for other clients. The separate TrackInfo status link is unchanged.

New tests execute the real generated loader through a production-style minified eval scope with decoy global player/item values, selected positive/negative/numeric IDs, cold asynchronous loading, invalid/missing IDs, native success/error notices and the standalone custom.js loader. Native TrackInfo tests check the selected-ID action, popup navigation contract and non-actionable verified result. This closes the test gap where only source names and direct calls into `api.love` had been exercised.

## Shared request queue, caches and removal (0.7.0)

The current [API rate-limiting reference](https://listenbrainz.readthedocs.io/en/latest/users/api/index.html#rate-limiting) requires each client to make no more than one call per second, in addition to observing the response limit headers. A plugin-wide asynchronous FIFO now spaces starts by at least 1.05 seconds and permits one active HTTP call. Settings validation uses the same queue. Queue capacity is 32; the 30-second operation deadline includes waiting and is checked again before dispatch, so expired POSTs cannot run later. A queued playing-now rechecks active, unchanged playback immediately before sending. Rate-limit exhaustion fails waiting calls without replay. Shutdown cancels timers and waiting requests.

This uses the upstream [LMS timer API](https://github.com/LMS-Community/slimserver/blob/1ceeaf1d601134f765b5a3e65113726284eaae6d/Slim/Utils/Timers.pm): high-resolution epoch deadlines with `setTimer(owner, when, callback)` and matching `killTimers`. No blocking sleep is used in the server.

Verified token ownership has a five-minute cache; verified feedback has a 30-second cache. Each has at most 128 entries, shared between Core instances/pages/players and separated by hashed username/token. Exact snapshot status reads coalesce while pending. Only successful, validated data is retained; token changes cannot reuse another credential's entries. Explicit refresh bypasses feedback cache. Writes invalidate account feedback before and after completion; a generation counter prevents older reads from repopulating it. Verified write readback seeds the new value. The frontend also invalidates pending read sequence numbers when a write starts.

The [feedback format](https://listenbrainz.readthedocs.io/en/latest/users/feedback-json.html) defines score zero as removal; minus one is dislike. Clicking the filled footer heart uses explicit `listenbrainzlove unlove`, not a toggle inferred by the server. Removal reuses the exact recent verified identity, including paired MBID/MSID, and requires targeted zero feedback for every supplied ID. Upstream deletion returns independent zero rows when the pair is absent; requiring a shared row after deletion would incorrectly report failure. Removal never creates playing-now. Unknown/uncertain responses do not change the heart optimistically or repeat a write automatically. The duplicate status action is removed from both Material context sections, while TrackInfo retains its separate read-only status link.

Tests use deterministic HTTP/timer fixtures for spacing, queue bounds, deadlines, cooldown, shutdown and playback revalidation; cache tests cover TTLs, credential separation, coalescing, mutation invalidation and late replies. Core tests exercise score-zero removal and split zero readback rows; Node VM tests execute the real click handlers and JSON command boundary. No real feedback is changed by these tests.

## Direct action, popup and optional desktop heart (0.6.0)

The [Material customisation reference](https://github.com/CDrummond/lms-material/wiki/07-Customisation) supports plugin `script` actions and user `custom.js`. Installed 6.4.14 `doCustomAction` evaluates scripts with the current `player` and selected `item` in scope; the action loader captures those values without `$ITEMID`/track-name interpolation. It loads the plugin's same-origin UI module, invokes the asynchronous JSON `listenbrainzlove action` and uses native `showMessage`/`showError` snackbar events only after a verified result. The original browse view remains unchanged. A separate native status entry is still read-only.

Material has no general plugin registration hook for the desktop playback-bar buttons; repeat/shuffle alternatives would replace existing service controls. The new independent heart instead uses an explicitly enabled managed loader in custom.js. The installer preserves the existing bytes, makes an exact backup, rejects incomplete managed markers and uses atomic replacement. Disabling removes only the managed block, preserving other additions. No Material core asset is replaced. The desktop footer uses the current track/player from Material's status events and native layout/colors; mobile layout is left unchanged.

The button reads feedback when track metadata/player identity changes; reads never post playing-now. Cold metadata gets at most one delayed read retry; rate limits and writes never auto-retry. Per-player pending actions suppress double clicks. Snapshot keys and sequence checks reject stale asynchronous replies, including changed radio metadata at the same track ID. A lost write reply stays uncertain and the next heart click reads status instead of repeating the write. Unknown state is never optimistically filled. Plain Node VM tests exercise the UI module's real asynchronous requests/events with fixture DOM and transport, without connecting to an account.

Version 0.6.1 fixes distribution timestamp invalidation discovered in the target LMS: reusing January 1 for every ZIP entry left a compiled settings template valid after the checkbox was added. The ZIP now uses an explicit per-release timestamp that remains fixed for reproducible builds and must advance for subsequent releases. The old/new settings entry mtimes and the live settings checkbox are checked during release verification.

The publication preparation reviewed the real [LyrionJS repo.xml](https://raw.githubusercontent.com/JameZUK/LyrionJS/main/repo.xml): `extensions/details/title` and `extensions/plugins/plugin`, attributes `name`, `version`, `minTarget`, `maxTarget`, and child elements `title`, `desc`, `creator`, `category`, `link`, `url`, `sha`. That example is on a mutable branch; it is a format example, not a pinned dependency.

The pinned LMS [PluginDownloader.pm](https://github.com/LMS-Community/slimserver/blob/1ceeaf1d601134f765b5a3e65113726284eaae6d/Slim/Utils/PluginDownloader.pm) imports `Digest::SHA1`; `_getDigest` opens the downloaded ZIP in binary mode and returns its SHA-1 hex digest. `_installDownload` compares that value with the repository's `sha`. Thus `repo.xml` uses **SHA-1 of the complete plugin ZIP**, not SHA-256 or a hash of source files. A separate SHA-256 manifest is provided for independent verification.

`tools/build.py` derives the version from `install.xml`, generates the plugin ZIP first, hashes it, then generates `repo.xml` and the source archive. This avoids a circular checksum dependency. The plugin ZIP does not contain `repo.xml`; the source archive does.


## Cold remote metadata and complete popup response (0.7.4)

TIDAL's [getMetadataFor](https://github.com/michaelherger/lms-plugin-tidal/blob/main/ProtocolHandler.pm) returns a bitrate/type/icon placeholder while its asynchronous track request populates the provider cache. It does not yet contain artist or title. Previously that placeholder reached Core immediately and failed with `Missing artist or title`; the next click then succeeded against the populated cache. The adapter now captures the selected source URL before yielding, waits for complete provider artist/title using LMS timers, and only then invokes Core. The wait is at most eight seconds, backs off from 250 ms to two seconds, and shares the original 30-second operation deadline with the API phase. Pending waits are bounded to 32 and cancelled at plugin shutdown. The per-player write lock starts before metadata preparation. Timer rechecks only inspect metadata; they never replay feedback. Status and removal use the same preparation path. Invalid selections, provider errors, inactive indefinite streams and timeout fail without a write or fake playback.

The installed Material 6.4.14 `browse-resp.js` converts a text result with any image/icon/svg into `type=other`. Its `browseHandleNextWindow` then falls back to the original action title. Popup-mode responses now omit the icon and remain one non-actionable text result; ordinary browse result/state rows retain their icons. Tests execute the complete, unmodified installed parser plus both text-action handlers against the actual generated success, failure and uncertain responses, including the native HTML wrapper and preserving the current detail view. This replaces the previous artificial already-parsed response fixture.

There was also a command-boundary defect: Material's `doTextClick` uses `lmsCommand` for this verb, so it does not insert list positions. The [LMS Request constructor](https://github.com/LMS-Community/slimserver/blob/1ceeaf1d601134f765b5a3e65113726284eaae6d/Slim/Control/Request.pm) consumes positional parameters before extracting tags. Read-only `state` commands reproduced the distinction with and without positions. The detail action explicitly sends `listenbrainzlove love 0 1` before the selected-ID and popup tags, preserving both. No live feedback writes are needed for these regression tests.


Version 0.7.5 corrects a regression discovered during the 0.7.4 live read-only deployment check: the high-resolution operation clock produced fractional `min_ts` values for recent listens, rejected by the existing transport allowlist before any HTTP request. Recent-listen timestamps now explicitly use whole seconds while operation deadlines retain high resolution. A fractional-clock regression reproduces the rejected URL and asserts the documented integer timestamp. The transport allowlist is unchanged.


## Plain-text native popup (0.7.6)

Material 6.4.14 adds a `<div style="margin-top:16px;margin-bottom:16px">` wrapper to a single non-actionable text response in `parseBrowseResp`, then forwards that title unchanged to the plain-text `showMessage` snackbar. The previous regression removed tags before comparing, masking the literal HTML shown to users. It now compares the complete emitted string exactly, including Czech messages and an invalid selection.

Popup-mode results remain a single text row without an image and include a genuine read-only status action. Material therefore preserves the plain title without adding its standalone-page HTML wrapper. The native `nextWindow:refresh` still consumes the result and retains song details. If another client follows the result action, it can only read status; it supplies both required list positions and can never repeat Love. An invalid selection has no selected-ID parameter and cannot fall back to the playing track. Non-popup browse result behavior is unchanged. No skin source, HTML rendering or additional API requests are introduced.
